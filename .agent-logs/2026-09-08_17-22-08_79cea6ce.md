## Reality check first

"Clone Amazon" is not a 24-hour scope. Amazon's actual surface area (marketplace/multi-seller, recommendations engine, fulfillment/logistics simulation, Prime, returns, live inventory across warehouses) is years of engineering. If this is an assessment, whoever wrote it expects a **credible slice**, not full parity. Treat the list below as "what real Amazon has" then explicitly cut most of Tier 2/3 or you'll ship nothing working.

Also — flag now, not after you build it: don't ship this with Amazon's actual logo/wordmark/product photos/copy. ## Where I'd push back on your stack

**Next.js for FE+BE** — agreed, and it's the right call given zero budget. Route Handlers/Server Actions replace a separate backend fine at this scale. One catch: Vercel's serverless functions have execution time limits (10s on Hobby) and are stateless — plan for that when you handle Stripe webhooks or any multi-step DB writes.

**Sanity as your product catalog — this is a mistake.** Sanity is a document CMS, not a transactional store. Orders need to decrement stock atomically or you'll oversell (two users buying the last unit simultaneously). A CMS with eventual-consistency writes and no relational integrity is the wrong system of record for price/inventory/orders. Use it *only* if you want CMS-editable marketing banners — otherwise drop it entirely. One less moving part to configure in a 24h window is a win anyway.

**"Vercel Postgres"** — heads up, Vercel deprecated that name; it's now Neon via the Vercel Marketplace integration. Functionally fine (serverless Postgres, connection pooling built in, which matters because serverless functions can't hold persistent DB connections), just don't go looking for a product that isn't called that anymore.

**Auth: pick one, don't leave three options open** — building custom auth (password hashing, reset flows, session handling) in this timeframe is hours you don't have and a common place to introduce security bugs. Between Clerk and Kinde: Clerk, purely because its Next.js integration needs less wiring under time pressure — cost/vendor lock-in would matter for a real product, but for a 24h assessment, minutes saved outranks that. Free tier covers this easily.

**Stripe test mode** — correct choice, no notes. Just remember webhook signature verification needs the raw request body, which Next.js Route Handlers require you to opt into explicitly (`bodyParser` config) — easy to lose an hour on this if you don't know it going in.

**Missing from your list: search implementation and caching strategy** — these are the actual "performance" story for a catalog site and you hadn't mentioned either:
- Postgres full-text search (`tsvector` + trigram index) — zero-cost, "good enough" relevance, no external service to configure. Skip Algolia/Meilisearch; not worth the setup time or cost for this scope.
- ISR (Incremental Static Regeneration) on product listing/detail pages instead of SSR-on-every-request — this is what actually makes a commerce clone feel fast, since product data changes rarely relative to traffic.
- `next/image` for the product images, non-negotiable — raw `<img>` tags will make the site feel slow immediately.
